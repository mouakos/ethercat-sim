2. System context

A real Beckhoff TwinCAT 3 PLC drives EtherCAT against the simulator over a real Ethernet cable. The simulator is our own software EtherCAT slave that emulates an entire station of terminals. The PLC has a normal, unmodified EtherCAT configuration and must not see a difference from real hardware.

Prior art (validation, not a dependency). The commercial acontis EC-Simulator does exactly this — a software-only slave-side simulator, "no special hardware… just a standard Ethernet controller," that runs a real master against virtualized SubDevices. It offers two coupling modes that map onto our plan: HiL (separate PC, real cable to the master) = our TwinCAT rig; SiL (replaces the NIC driver, fully virtual) = our future pysoem harness. Two takeaways shape our design: (1) a real master driving a software slave over a cable is a shipping, proven configuration — Milestone 3 is achievable in principle. (2) acontis lists TwinCAT support "with add-on license" — but that add-on is only for SiL (same-host software bridging); HiL over a real cable needs nothing special on the master, because TwinCAT just sees a real EtherCAT network on its NIC. That is precisely why our approach works and why TE1111 was never required. acontis hits "1 ms and even below" using a kernel real-time Ethernet driver; we use userspace Npcap, which bounds us to looser cycles (see §4.5 and the cycle-tier risk). We deliberately hand-roll our slave stack (clean license, learning value) rather than build on Beckhoff's ET9300 Slave Stack Code as acontis does — so EC-Simulator is a reference design, not a component we consume.
The central challenge: a real EtherCAT slave uses an EtherCAT Slave Controller chip (ET1100, LAN9252, …) that processes frames in nanoseconds while they pass through. We are doing this in software on a generic NIC, in microseconds. Whether TwinCAT will accept our timing at a 10 ms cycle is the make-or-break question, gated by HANDOVER §4 Milestone 3.

3. Layered architecture

Layer responsibilities

LayerResponsibilityLang

L3 Mailbox CoE (mandatory), EoE/FoE (optional). Dispatches to device-model object dictionaries via L3.5. C++
L3.5 Bridge In-process IPC between the C++ slave core and the L4 device-model service: shared memory + futex / cond-var for cyclic PD (hot path), gRPC for SDO and IO-Link slow path. C++ C# Python
L4 Device models Per-device object dictionary, PDO mapping logic, profile state machines (e.g. CiA 402), IO-Link master logic and downstream IO-Link device behavior. Slow path; need not be real-time. C# Python
L5 Scripting & config YAML topology, scripts, event injection, replay. Python
L6 Observability Live values, logs, metrics, simple web UI. Python

4. The slave core in detail

This is where the project's risk concentrates. A short overview of what L2 must do per slave in the chain.

4.1 Chain emulation

Our process holds one or more logical slaves. Frames arriving on the NIC are processed sequentially: each slave reads/writes its own area, increments the Working Counter where it matched, and "passes" the frame to the next slave. The first slave's "output" port is what we send back on the wire (since we have only one NIC port, the chain terminates inside us).

Each slave has an identity: vendor ID, product code, revision, station alias, configured address. The master assigns the configured address during the Init phase via APWR datagrams to register 0x0010.

4.3 SII (EEPROM) emulation

Each slave has a virtual EEPROM containing its identification, mailbox config, and PDO/SyncManager defaults. The master reads this via the SII access registers (0x0500–0x050F) during Init. Our EEPROM contents come from Beckhoff's ESI XML for the imitated terminal — parsed at startup, stored in memory per slave.

4.4 ESM (EtherCAT State Machine)

The init-command sequence — the concrete recipe for reaching OP. The master does not improvise. From its compiled network description (the ENI, generated from the project topology + each slave's ESI), TwinCAT derives a fixed, ordered list of register reads/writes it sends every slave to walk it Init→PreOp→SafeOp→Op. Reaching OP is therefore not an open-ended problem: it is satisfying that exact list. The sequence, per slave, is roughly:
  1. Detect & configure data link — BRD of AL Status (0x0130); DL Control writes (0x0101) setting the port loop config.
  2. Assign station address — write the configured-station-address register (0x0010), after which the slave is addressed by FPRD/FPWR.
  3. Read identity — SII/EEPROM reads (0x0500–0x050F) for vendor ID, product code, revision.
  4. Configure SyncManagers — write SM registers (0x0800+): mailbox SMs for PreOp, process-data SMs for SafeOp.
  5. Configure FMMUs — write FMMU registers (0x0600+) mapping our PD into the master's logical image.
  6. Walk AL states — write AL Control (0x0120); we ack via AL Status (0x0130) or reject with a code in AL Status Code (0x0134).
This list is not a guess — TwinCAT shows it to us. Each slave's Advanced Settings → Init Commands tab in TwinCAT XAE enumerates the precise datagrams (and a captured trace confirms them on the wire). The slave-core build order (Milestones 2–3) is exactly this list, top to bottom; each step is "done" when the master's working counter for that datagram comes back satisfied and it proceeds to the next.

4.5 Distributed Clocks (the careful approximation)

Real ESCs latch the master's reference clock into a register every time a frame passes — at nanosecond precision because it's gate-level hardware. In software we cannot do this faithfully. Our approach:

  • Respond to the master's DC datagrams (system time read, propagation delay measurement) with synthesized values consistent with our position in the chain.
  • Use the host's monotonic clock plus a per-slave offset to fabricate a stable system-time read.
  • Do not attempt to drift-correct against the master at sub-millisecond precision.
  • Goal: pass the master's plausibility checks; reach Op; stay there. Phase-accurate DC is a non-goal.

This is Risk #2 (after raw cycle timing). If TwinCAT enforces stricter DC behavior than expected, we will surface that during Milestone 3 and decide.

5. Process & deployment view

Three processes on the simulator host:

  1. Slave core (C++) — L1, L2, L3. Pinned thread, real-time–leaning. Owns the NIC.
  2. Device model service (C# or Python) — L4. Connects to the slave core via shared memory + gRPC.
  3. Control plane (Python) — L5/L6. YAML topology, scripts, observability.

The PLC laptop is the fourth process, externally, on the other end of the cable.

6. Frame & data flow (cyclic read)

PLC master  --[LRD/LRW datagram]-->  L1 wire (our NIC)
L1 wire     --[parsed frame]-->      L2 slave core
L2          per slave in chain order, applies SM/FMMU,
            reads PD from the shared region into the frame
L2          builds response, marks WKC, hands to L1
L1          --[raw frame]-->          PLC master

In parallel (slow path):
L5 script   --[ZeroMQ]-->             L4 device service
L4          updates its PD copy (e.g. new sine value)
L4          --[shm write]-->          L2's PD region
(next master cycle reflects the new value)

7. Test architecture

Two distinct test rigs.

7.1 Headless harness — SOEM-based

For CI and fast regression: a Python test driver using pysoem (Cython wrapper for SOEM). The harness binds a NIC (or a virtual NIC pair in a Linux network namespace), scans the simulator's bus, walks the slaves through ESM transitions, exchanges process data, and reads CoE objects. No TwinCAT involved.

A green CI does not prove "TwinCAT will work" — only that our simulator behaves like an EtherCAT slave. TwinCAT-specific acceptance is gated by the real-PLC rig below.

SOEM is GPLv3 (dual-licensed commercially). Because the harness is an internal test tool, GPL obligations are trivial.

7.2 Real-PLC rig — TwinCAT-driven

The TwinCAT laptop runs the phase-1 PLC project. Test cases are Python scripts using pyads against the PLC laptop's TwinCAT runtime: read/write PLC-side variables, check expected behavior end-to-end. This is the authoritative acceptance test.

Cadence: on every milestone gate (phase-1 acceptance, phase-2 acceptance), and weekly during active development.

8. Cross-cutting concerns

Determinism

  • L1–L3 in C++, pinned to an isolated CPU on Linux (isolcpus + SCHED_FIFO). On Windows, raise process and thread priority and disable interrupt moderation on the NIC.
  • No allocations on the hot path. Preallocate PD buffers per slave at startup.
  • Document tolerated cycle jitter and surface it as a metric in L6.
  • Consider PREEMPT_RT kernel for Tier 2/3 cycle-tier work.

Testability

  • L2/L3 testable headless with pysoem.
  • L4 testable with table-driven object-dictionary unit tests.
  • Real-PLC rig is the authoritative acceptance gate.

Observability

  • Structured logs (JSON) from every layer with a session id.
  • Live PDO view in L6; per-slave counters: cycles served, mailbox req/resp, errors.
  • Wireshark dissector for our session logs (frames + state-machine events on a common timeline).

Extensibility

  • New device class = new L4 device model + new entry in YAML config + (maybe) new ESI / IODD reference. No L2/L3 changes expected for new device classes that fit existing patterns.
  • Junction terminals (EK1521 / EK1122) are a future L2 feature — chain branching, not just linear.

Licensing & legal

  • We are not shipping an EtherCAT product — no ETG membership or Vendor ID needed.
  • Our slave-side code is original; we do not pull in SOES (GPLv2) so the slave is free of viral copyleft.
  • SOEM is GPLv3 with a commercial option; we use it only in the headless harness (a separate internal tool), so obligations are easy.
  • Beckhoff ESI files for EL terminals are freely distributed; we may reference them and use the Beckhoff vendor ID (0x2) in our EEPROM mirrors, because we are impersonating their devices for testing — not selling our own.
